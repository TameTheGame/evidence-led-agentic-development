## Final reply

Added seven climb requirements to `spec/outpost.spec.md`, interleaved by rung to match the file's existing order, plus two cards.

```
OUT-CLIMB-01  static   agreed  the layout's climb runs unbroken from the tower route to the tower top
OUT-CLIMB-02  engine   agreed  every climb surface in the generated tower has collision
OUT-CLIMB-03  engine   agreed  a player-sized capsule travels the whole climb to the top
OUT-CLIMB-04  engine   agreed  the tower top holds a standing player clear of the drop
OUT-CLIMB-06  session  agreed  a remote client can climb to the top          (card CLIMB-1)
OUT-CLIMB-05  engine   draft   a player who reaches the top can get back down unhurt
OUT-CLIMB-07  owner    draft   the way up reads at a glance, the climb isn't fiddly  (card CLIMB-2)
```

**Agreed on your behalf** under the 2026-11-01 hand-off in `docs/DECISIONS.md` ("For the tower climb work, agree the requirements you draft for climbing the tower on my behalf. This holds until the climb ships."): the five above, each carrying an `agreed-by` field quoting it. Change or retire any of them — that stays yours, the hand-off doesn't cover it.

**Two left draft, deliberately:**

- **OUT-CLIMB-05 (getting back down).** Getting down isn't climbing, so the hand-off doesn't reach it — but a tower with no way down is a trap. Do you want descent as a requirement, or is jumping off (or dying) acceptable?
- **OUT-CLIMB-07 (how the climb reads and feels).** I can write that the way up should be obvious, but not decide what the climb should feel like. Should it read as easy and inviting, or as a bit of a scramble the player earns?

**Why the rungs split this way:** the existing agreed requirements don't cover the climb. OUT-COLL-01 is about flat walkable floors, and OUT-ROUTE-01's own `why` says listed segments are flat and stairs need a walk test instead — so steps, ladders and landings would have gone unchecked. OUT-SAVE-01 already covers the climb geometry surviving save and reopen, so I added no editor requirement. OUT-SIGHT-01 already proves the top is *visible*; nothing proved it was *reachable*.

**Check run:** `py -3 tools/spec_lint.py --sources tools` → `PASS - 16 requirements well formed`. It reports `NEEDS OWNER` for exactly the five I agreed, which is the gate working as intended; the hand-off is the answer to it. It also reports `NOT FOUND` for all ten machine checks, including the six that predate this change — neither the generator nor `UnitTests/` is in this folder, so no check name resolves here. That's the lint's non-blocking lookup, not a new problem.

**What is *not* done:** these are requirements only. `spec/outpost.layout.json` still has no climb data (the tower is just a `top` point at `[400, 0, 480]`), the `lint-layout OUT-CLIMB-01` rule isn't written, and the three engine tests don't exist — and can't be run here anyway, per AGENTS.md. One note for whoever writes the lint rule: OUT-CLIMB-01's rise limit must be read from S&box's `PlayerController` step height rather than guessed, since the engine source isn't available in this environment.

I haven't committed anything — the change is in the working tree, which is what keeps the owner gate reporting those five until you've seen them.
