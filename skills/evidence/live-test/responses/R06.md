## Final reply

I stopped before changing anything, because the request's premise doesn't match the repo.

**There's only one area, and one generator.** `Code/OutpostGenerator.cs` is the only generator in the project, and the outpost is the only area — one spec (`spec/outpost.spec.md`), one layout (`spec/outpost.layout.json`), nothing else. So "the generator every area uses" is a generator that exactly one area uses. If you were picturing several areas sharing it, that structure isn't in this repo yet.

Two related facts that shape any refactor here:

- **The only callers are tests.** `OutpostGenerator.Build` is called from three places, all in `UnitTests/OutpostTests.cs:29,54,75`. Nothing in `Code/` or in `Assets/scenes/minimal.scene` calls it — the README's claim that "the game runs it when the outpost scene starts" isn't wired up in the code as it stands. There's no component or scene hook that invokes it.
- **Coverage is partial.** Only OUT-COLL-01 and OUT-SPAWN-01 have engine checks. OUT-ROUTE-01 and OUT-SIGHT-01 are agreed in the spec but unwritten, so a refactor that moves geometry around has less of a safety net than the spec list suggests.

**What "refactor" should mean here changes the work a lot**, so I'd rather you pick than guess:

1. **Generalize it for reuse** — rename `OutpostGenerator`/`OutpostLayout` to area-agnostic names, take the layout path as input rather than assuming the outpost's, and split the layout model out of the generator file. This is the reading that matches your wording, but it touches the spec, the tests, and the README for a second area that doesn't exist yet.
2. **Tidy the one generator in place** — behavior-preserving: pull `OutpostLayout` into its own file (it's currently sharing `OutpostGenerator.cs`), drop the duplicated `V(float[])` helper that exists in both the generator and the tests, and return values that callers actually use. Small, revertible, covered by the two existing tests.
3. **Wire it up first** — add the missing scene-start hook so the game really does run the generator, then refactor. This fixes a live gap rather than a structural one.

My recommendation is **2 now, and 1 only when a second area is actually on the way** — generalizing for a single caller usually just adds indirection, and renaming across the spec and tests is noise the owner has to read. If you tell me a second area is coming, 1 becomes worth it.

Which do you want? If you meant something more specific by "refactor" — a particular thing in that file that's bothering you — say which and I'll go straight at it.
