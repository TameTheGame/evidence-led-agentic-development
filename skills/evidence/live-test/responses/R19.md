## Final reply

Fixed and proved at the engine rung.

**Cause.** `OutpostGenerator.AddMeshBlock` created the `MeshComponent` already enabled and assigned `Mesh` afterwards. Outside an editor scene, `MeshComponent` builds its model only at the moment it's enabled, so every block got a `GameObject` and a component but no model and no collision shapes. Nothing errored — the engine log shows 0 component errors — the geometry simply was never built. The yard floor felt solid because the ground is a `BoxCollider`, not a mesh block, which is why only the walls seemed wrong. The project's own `UnitTests/StarterGeometry.cs:43` already carries the correct pattern as a comment; the generator just didn't follow it.

**Change.** `Code/OutpostGenerator.cs:48` — create the component disabled, assign `Collision` and `Mesh`, then enable it.

**Evidence.** I wrote `UnitTests/OutpostTests.cs` first and watched it fail for the right reason, building the real outpost through `OutpostGenerator.Build` from the real `spec/outpost.layout.json`:

| Check | Before fix | After fix |
|---|---|---|
| `Outpost_EveryMeshBlockHasCollision` | FAIL — no collision geometry for all 7 blocks | pass |
| `Outpost_WallsBlockAPlayerBody` | FAIL — "wall.north: a player body swept straight through it" | pass |
| `Outpost_GateGapIsOpen` (control) | pass | pass |

The body sweep is the same trace the player controller makes when it moves, so a sweep reaching the far side is a player walking through. The gate-gap control passes in both runs, so the wall check isn't just hitting everything.
