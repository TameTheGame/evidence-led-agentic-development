## Final reply

The test is written at `UnitTests/OutpostTests.cs:19`, named after the check the spec gives (`OUT_SPAWN_01_EverySpawnLandsOnSolidGround`). It reads `spec/outpost.layout.json`, builds the area with the game's own `OutpostGenerator.Build`, and for each spawn in the data: drops a player, asserts it lands, asserts it lands on the yard's ground (`layout.Ground.Max.z`, ±2), and asserts its standing body isn't inside geometry.

It ships with two controls, and one of them is red for a real reason.

```
OUT-SPAWN-01  engine  PARTIAL  (uncommitted)  lands-on-ground proven; room-to-stand is blind — generated blocks have no collision
```

| Test | Result |
|---|---|
| `OUT_SPAWN_01_EverySpawnLandsOnSolidGround` | pass — both spawns land at z ≈ 0 |
| `OUT_SPAWN_01_Control_SpawnOverTheVoidIsDetected` | pass — the landing check can fail |
| `OUT_SPAWN_01_Control_SpawnInsideGeometryIsDetected` | **FAIL** — a player standing inside the tower is not detected |

Full suite: 7 of 8 pass, that control the only failure (`test-results/20261012-191122`).

**Cause of the red control.** Not the test: `OutpostGenerator` builds no collision at all. A diagnostic over a generated scene printed `model=null` for all seven blocks — walls, gate apron, tower — while a trace down the tower's centre hit only `ground`. The same tower box, same scene, built the way `StarterGeometry.CreateBlock` does it, gets `collisionMeshes=1`. The difference is `Code/OutpostGenerator.cs:48` — `Components.Create<MeshComponent>()` creates it *enabled* and assigns `Mesh` afterwards; outside an editor scene the mesh only builds on enable, so the assignment does nothing. `StarterGeometry.cs:44` documents exactly this trap.

So the main test's "room to stand" assertion currently passes vacuously — it can only see the ground box collider. I left the control red rather than softening it; that red is the honest state of the check. It also means OUT-COLL-01 will fail for the same reason when you get to it.

**The fix** is two lines in `AddMeshBlock`, mirroring the starter:

```csharp
var block = go.Components.Create<MeshComponent>( false );
block.Collision = MeshComponent.CollisionType.Mesh;
block.Mesh = BoxMesh( size );
block.Enabled = true;
```

I checked what that would do without touching game code — a stand-in build with the correct order, same layout data: both spawns land at z = 0.04, neither stuck, and the inside-tower control detects correctly. So all three tests go green and the pass becomes meaningful. Want me to apply it, or does it belong with the OUT-COLL-01 work?

One limit worth stating: this is the engine rung only. It proves collision, landing height, and clearance headlessly — not that the outpost looks right or plays right.
