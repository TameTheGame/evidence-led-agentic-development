## OUT-SPAWN-01 — engine check written

`UnitTests/SpawnTests.cs` builds the outpost with the real generator from `spec/outpost.layout.json`, then splits the requirement into three probes per spawn:

1. **Solid ground within a short drop** — ray down from the spawn, `MaxFall = 64`.
2. **Room to stand** — a 32×32×72 box hull (PlayerController's default body) at the landing spot, plus a swept version of the same hull down the drop so a snag on the way is caught too.
3. **Not buried** — out-and-back ray probe to the sky.

Probe 3 is there because of the hollow-mesh-collision rule from `[skill]`: a body wholly inside a mesh block touches no face, so a spawn placed deep inside the tower would sail past probe 2. Out-ray misses (faces aren't seen from behind) + back-ray hits ⇒ buried. A spawn under a legitimate roof is blocked both ways, so it isn't flagged.

**Three control tests ship with it**, because I can't watch this check fail myself:

| Control | Point | Must report |
|---|---|---|
| `Control_BodyInAWallIsBlocked` | straddling `wall.north` | blocked |
| `Control_PointInsideTheTowerIsBuried` | inside `tower` | buried |
| `Control_PointInThinAirHasNoGround` | 400 units up in the yard | no ground |

If a control is red, the spawn green means nothing — each one carries a comment saying that and where to look.

Both would make the wall and tower controls fail — which is the controls doing their job, not a layout problem:

- **No `default` physics surface.** Base content isn't mounted in headless tests, and `PolygonMesh.Rebuild()` needs a `default` surface even when no collision is asked for. `UnitTests/` has no stand-in (the spike kit's `TestSurfaces.cs` isn't in this repo). This blocks every engine check in the spec, not just this one.
- **`MeshComponent` enable order.** `OutpostGenerator.cs:48-50` creates the component enabled, then assigns `Mesh` — in a game scene the model only builds on enable, so the walls and tower may have no collision at all. That's OUT-COLL-01's territory, so I left the generator alone.
