## What was wrong

`AddMeshBlock` gave each block a `MeshComponent` and set `Collision = CollisionType.Mesh`, but no collider component. A mesh built in code at runtime gives the physics world nothing to collide with from that flag alone — so the walls rendered but weren't solid. `AddGround` was the tell: it's the one piece that works in game, and it's the one piece with a real `BoxCollider`.

**This also affected `gate.apron`** — a walkable floor players would fall through, not just the walls.

## The fix

`Code/OutpostGenerator.cs:42` — each block now gets a `BoxCollider` with `Static = true`, exactly the pattern the working ground uses. Every block in the layout is an axis-aligned box, so the collider matches the mesh exactly rather than approximating it. The block object now sits at the box centre and `BoxMesh` is centred on its local origin to match, so world geometry is unchanged and no collider offset is needed. I deliberately used only API already proven in this file (`BoxCollider.Scale`, `.Static`, `Components.Create`) and dropped the one uncertain call.

`UnitTests/CollisionTests.cs` traces the built scene rather than trusting geometry. Three assertions that cross-check each other:

- **ground down-trace** — exercises a `BoxCollider` that already works in game, so a failure here means the test setup is broken, not the fix.
- **wall cross-traces** at chest height, plus every block top from above (catches the apron).
- **gate opening must *not* hit** — the negative control. If that one fails, the traces hit everything and the wall check proves nothing.

I have not seen these fail for the right reason, because I can't run them. They also use `scene.Trace.Ray(...).Run()`, `trace.HitPosition` and `trace.GameObject`, which I couldn't compile-check — if a name is off you'll get a build error immediately rather than a wrong pass.
