## Root cause (static rung — reading only, not engine-verified)

`Code/OutpostGenerator.cs` created the `MeshComponent` **enabled**, then assigned `Mesh` afterwards. Per `[skill]`, in a game scene that builds no model and no collision — the assignment is a no-op. So every mesh block came out non-solid.

Why that reads as *"near the gate"* specifically: the yard floor is a `BoxCollider` (`AddGround`), which is unaffected, so inside the walls you always land on something. `gate.apron` spans `y −1024…−800` — **outside** the ground box — and is the one walkable floor built as a mesh. The gate route runs out to `[0, -900, 0]`, right onto it. It's the only place in the layout where losing mesh collision means losing the floor.

This also predicts the walls and tower were non-solid too — a walk-through, not a fall-through, which a tester may simply not have hit. That prediction is the cheapest way to confirm or kill the diagnosis, so it's step 2 of the card.

## What changed

- `Code/OutpostGenerator.cs:48` — create disabled → set `Collision` → assign `Mesh` → enable.
- `UnitTests/CollisionTests.cs` — new, implements `OUT_COLL_01_EveryFloorHasCollision`, the check `spec/outpost.spec.md:33` names but which was never written. Rays down onto the ground top and every block top level with it, on a 32-unit grid (a player hull, so no fall-through-sized hole hides between probes), skipping points under taller blocks. It has two anti-vacuity guards: it fails if a floor yields no probe points, and it fails if any listed route point isn't over a floor it probed.
