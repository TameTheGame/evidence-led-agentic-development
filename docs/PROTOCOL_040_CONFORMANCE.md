# Protocol 0.4 Conformance Contract

Protocol 0.4 is a versioned Level 0 evolution of the Evidence-Led Agentic Development
blueprint. It is a platform-neutral reference contract and conformance corpus—not a live
controller, approval service, model runner, target adapter, lease backend, evidence
authority, promotion service, or proof that any real model/harness is qualified.

The frozen `v0.3.0` release remains the compatibility predecessor. A target pinned to
0.3 remains bound to that exact protocol; adopting 0.4 requires an explicit repin and
rerunning the target-owned checks affected by the changed review-flow contract. Mixed
protocol chains are denied. The preserved non-normative episode drafts remain identified
as 0.3 historical artifacts and are not part of the 0.4 authenticated bundle.

## The central 0.4 correction

Version 0.4 retains three orthogonal decisions:

1. **Project capability maturity:** the maximum infrastructure/effects the target has
   empirically proven.
2. **Task rigor:** `light`, `bounded`, `evaluated`, or `assured`, selected from
   uncertainty, complexity, reversibility, consequence, per-claim evaluator maturity, and
   delegation distance.
3. **Effect authority:** the exact read/write/runtime/data/promotion effects the
   owner-local episode may exercise.

A maturity level never forces maximum per-task ceremony. A rigor decision never grants
authority. A model certificate never overrides the target.

Within that separation, assurance must minimize expected lifecycle cost while still
meeting the claim's acceptance threshold. Quick review permits at most one critic pass;
standard review permits one complete review/correction cycle; high assurance permits at
most two. Corrections consume the current budget, and candidate creation, renaming, or
reframing never resets it. Extra cycles require either high-consequence uncertainty plus
new objective evidence or fresh owner authorization after cost and expected benefit are
reported. A correction invalidates only the claims and evidence in its causal footprint;
ordinary tracked artifacts use Git identity and clean/dirty state, and qualified local
checks are preferred when they can answer the claim reliably.

## What the strict assurance modules protect

The optional `assured` protocol retains strong controls for cross-context,
high-consequence autonomy:

1. **Target authority stays primary.** Effective authority is the intersection of
   owner-local workflow, profile, policy, exact qualified scope, tools/evaluators,
   requested effects, and any required writer lease.
2. **Maturity constrains effects.** Promotion and publication remain unavailable in the
   executable 0.4 reference because no reviewed contract exists for either.
3. **Context means delivered bytes.** Source identity, delivery bytes, ordered
   model-visible segments, and bounded context continuation are distinct authenticated
   records when strict context proof is required.
4. **Qualification is empirical and non-Cartesian.** A request must fit one measured
   model/runtime/harness/adapter scope row. Two worker harnesses and an orchestrator
   harness are distinct subjects.
5. **Material resources are part of the subject.** Configured, requested, measured-safe,
   and observed envelopes are compared only when those dimensions matter.
6. **Evidence binds the exact subject.** The receipt authenticates its evidence manifest
   and resolved candidate; wrong/stale neighboring evidence cannot close a claim.
7. **Human review binds what was actually shown.** Retained human closure references a
   sealed review bundle and eligible reviewer.

These records are conditional. There is no normative integrated `assured` episode
contract in 0.4: the preserved schema/template are non-normative drafts because structural
validity does not prove cross-component semantic admission. They are not a universal task
format or conformance evidence.

## Adaptive task path

The platform-neutral development loop is:

```text
learning question -> important uncertainty -> cheapest reliable evidence
  -> smallest useful build -> observe -> evaluate -> analyze errors
  -> choose next change -> repeat or stop
```

A light task may use only an issue/prompt, deterministic check, and diff. A bounded task
uses a compact handoff. Evaluated work adds error analysis and iteration plus only the
semantic, runtime, evaluator-calibration, or stateful-recovery modules selected by its
claims and effects. Assured work adds strict contracts, independent expectations,
malicious cases, recovery, and separate activation; it does not imply runtime evidence or
rollback proof when those are inapplicable.

Evaluator maturity is bound per claim class. A new exact regression does not become an
unproven fallible evaluator merely because it is new. Executing a program does not by
itself create a runtime/operational claim, and an AI coding worker does not by itself
create stochastic product behavior.

## Reusable calibration

Protocol validators, path corpora, lifecycle rules, malicious vectors, schemas, and
evaluator calibration packs are amortized infrastructure. They can run cheaply in CI.

Per-task manifests, packets, full receipts, negative suites, model qualifications,
review bundles, leases, and adversarial reviews are selected only when their triggering
uncertainty or consequence exists. Stable calibration is cited until a named drift event
requires the affected slice to rerun.

## Lifecycle conformance

The external receipt transition table contains 33 admitted rows across seven dimensions
whose full Cartesian product is 44,100 tuples. The number describes exhaustive
closed-world negative space, not 44,100 realistic authored scenarios.

Version 0.4 retains a separate rules-derived admission predicate that does not read
the table, compares both verdicts over every tuple, and uses focused vectors for claim
aggregate semantics, all 15 unique admitted shapes, and single-field denials across all
seven dimensions. This is cheap reusable protocol conformance. It applies only to formal
assured receipts.

## Provider and harness neutrality

The shared protocol names measured capabilities, resources, tools, evidence, and effects,
not vendor prestige.

- A cloud orchestration profile is shaped for long-horizon planning, delegation, and
  compact receipt inspection. Repetitive tool traces should be delegated.
- A constrained local profile receives one small precompiled objective, bounded context,
  fixed tools, output/resource budgets, a supplied evaluator, and no recursive spawn by
  default.
- The exact model, runtime, harness, adapter, prompt/context compiler, tool schema, and
  material configuration form the subject.
- Coding-agent and product-inference harnesses are separate subjects even when they load
  the same model weights.
- A supervised one-off light route can be owner-bounded without creating a transferable
  certificate; repeated autonomous routing needs empirical qualification.

## Authoritative serializer rule

The neutral rule for opaque target-owned formats is:

```text
reviewable high-level input -> target-owned public serializer -> save/reload
  -> logical and complete-resource verification
```

Agents never synthesize, patch, merge, structurally interpret, or partially copy opaque
bytes as an external authoring format. Target-specific examples belong outside this
normative protocol.

## What Level 0 can and cannot prove

The Level 0 suite can prove internal reference properties such as:

- schema/template and closed-inventory integrity;
- default-deny/reference-only state;
- canonical/raw digest framing;
- path grammar conformance;
- lifecycle table/rule agreement;
- synthetic context, authority, budget, adoption, and malicious-case semantics;
- adaptive-rigor selector invariants.

It cannot prove a real model, harness, target adapter, runtime, reviewer decision,
operating-system matrix, workflow efficacy, or product behavior. Those are target-owned
empirical gates. Unrun is not failed, but it is never passed by inference.

## Release conditions

Protocol 0.4 may be called a reviewed Level 0 blueprint only when:

1. the explicit normative inventory is authenticated by the release bundle;
2. templates remain inert and examples remain synthetic;
3. all dependency-free conformance suites pass;
4. the exact commit passes a fresh-checkout proof;
5. one bounded adversarial review of the frozen candidate reports no unresolved material
   flaw after any authorized correction;
6. Level 1+ empirical probes and absent operational surfaces remain durably listed.

A review does not activate any target or accept any external project's architecture gate.
