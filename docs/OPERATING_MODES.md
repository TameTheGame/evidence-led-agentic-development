# Operating Modes

Direct and Conserve choose how authorized work is delivered. They are independent of
`light`, `bounded`, `evaluated`, and `assured` rigor, project maturity, and effect
authority. This is provider-neutral guidance for a Level 0 reference blueprint; it
implements no model router or target operation.

## Choose once for a coherent outcome

Use Direct for ordinary user-directed delivery unless the owner or current project
workflow selects Conserve. An explicit cost or local-execution preference selects
Conserve only within the allowed data, subject, and effect boundaries. Explain a
material routing tradeoff; do not turn routine mode selection into an owner questionnaire.

| Mode | Delivery responsibility | When extra machinery helps |
|---|---|---|
| Direct | The capable primary agent owns inspection, implementation, checks, causal repair, and completion within the authorized outcome. | Delegate a bounded independent subtask when it adds useful parallelism, expertise, or justified independent verification. |
| Conserve | Deliberately route bounded work to a qualified cheaper or local subject and retain responsibility for integration and verification. | Use the selected worker's measured context, tools, budget, verifier, and candidate limits. |

Direct can use high rigor. Conserve preserves the same acceptance threshold. A local
subject may be highly capable, and a cloud subject may be economical; hosting alone
does not choose the mode. Deterministic tools remain useful in either mode.

## Direct delivery

Infer the next implementation steps from the request, project rules, and current facts.
Complete the scoped inspect/change/run/inspect/repair loop before handing back the result.
Use existing authorization for routine fixes and checks; seek a decision only when
missing intent, authority, or a material tradeoff changes the outcome. A new governed
effect still needs its applicable grant.

Read instructions and source progressively as the task requires them. Ordinary Direct
source work needs no mandatory packet, compiler, worker, certificate campaign, or
separate model for each role. This includes user-directed `light` and `bounded` work:
lack of a reusable autonomous capability certificate does not block that source path.
A successful task creates no transferable qualification.

Select checks by risk and the claim. Run required checks and inspect results. Add tests
only when they can detect a realistic failure; do not mirror the implementation or keep
expanding verification of a reversible low-risk edit after sufficient evidence exists.
New failures, changed code, or unresolved material concerns justify affected rechecks.

## Conserve and constrained delegation

Select the exact eligible subject and verifier for the task. Use the existing
[qualification guidance](MODEL_QUALIFICATION.md) for repeated autonomous routing,
delegated deployment, or capability claims. An explicitly supervised one-off experiment
remains an experiment and cannot be relabeled as a qualified route.

When a constrained worker is selected, supply one bounded objective, selected context,
capped tools and outputs, explicit attempt/time/resource budgets, a supplied verifier,
and candidate isolation appropriate to its allowed effects. Reuse the
[bounded worker packet](../templates/BOUNDED_WORKER_PACKET.template.md) when a saved
handoff is useful; use strict protocol records only when their triggers apply. These
worker controls also apply to a constrained delegate selected during Direct.

Prefer the eligible cheaper or local route within an explicitly selected Conserve
assignment. Do not silently change the subject, model, quantization, budget, privacy
boundary, or fallback policy after failure. A cloud pass is not an automatic duplicate
of sufficient local evidence. Report a causal failure or routing limit and continue
only within the existing scope and attempt budget.

## Shared controls and role boundaries

Both modes preserve actual owner authority, privacy and data policy, exact native
executors and opaque serializers, required fencing, independent evidence, retained human
judgment, and separate finalization, promotion, and publication. Local execution alone
does not prove restricted-data isolation. A mode name grants none of these capabilities.

Logical roles describe responsibilities, not a requirement to instantiate separate model
agents. The primary agent may implement and run trustworthy checks within one authorized
source task. Use separate independent verification when consequence, circular evidence,
or the applicable effect contract warrants it. An orchestration-only or candidate-only
grant cannot silently become target, promotion, or evidence-acceptance authority.

Repeated autonomous deployment in either mode still requires evidence for the exact
model/runtime/harness/context/tool/resource subject and allowed task class. Preserve
existing certificates, runtime qualification, fixtures, and their invalidation rules;
a newer model or one successful Direct task does not supersede them. Review budgets and
claim-scoped revalidation remain governed by [Adaptive Rigor](ADAPTIVE_RIGOR.md#proportional-assurance-budgets-and-causal-revalidation).

## Audit disposition and adoption evidence

Retain the evidence-led learning loop, exact expectations, lifecycle lessons, and
effect boundaries because they prevent demonstrated classes of failure. Simplify blanket
document preloads, obligatory worker routing, and repetitive review because they add cost
without necessarily improving the current decision. Keep constrained-worker packaging
conditional on the selected route because model and harness needs differ.

Treat a Direct trial as an adoption observation, not evidence of model superiority.
Compare accepted tasks with comparable scope, rigor, and authority. Record model traffic
(input/output and cached versus uncached tokens where available), repair attempts,
orchestration work, elapsed time, human intervention, and acceptance results per task.
Report missing measurements and pricing assumptions; traffic is not automatically
billable cost. Keep private source, user paths, logs, and target evidence in their owner
repository. This guidance adds no benchmark, telemetry service, or selector schema.

explains the prompt audit that informed this correction. It does not select a provider
for ELAD or change any installed runtime.
