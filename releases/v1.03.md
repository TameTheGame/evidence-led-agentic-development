# ELAD v1.03 — A major number for breaking changes

This release settles what happens to the version number when a release breaks existing
projects. No skill changed, and no example changed.

## Highlights

- **Breaking changes take a new major number.** A release that breaks existing projects
  goes to the next major number: the first after `1.xx` is `2.0`, then `2.01`, `2.02`,
  and so on. Every other release takes the next two-digit minor number, as `1.01` to
  `1.03` did. See [Releasing](../docs/RELEASING.md#version-numbers).
- **What counts as breaking.** A change breaks existing projects when a project that moves
  to it has to change its own files, beyond its pin and the copies it takes, for its specs
  and checks to keep working. A renamed spec field or an example script whose arguments
  changed would count. Such a release's notes say what broke, what a project must change,
  and how to stay on the previous release.
- **Recorded as a decision.** ADR-0021 in [Decisions](../docs/DECISIONS.md) now covers
  this rule as well as the two-digit numbers and the release for each update. Until now
  the policy said what a breaking change does only in `0.x`.

## Compatibility and migration

Nothing in the core breaks. The three skills and the example domain skill are unchanged
since v0.8, and no example script or document changed.

- **Update your pin.** A project that names its ELAD version changes it to `1.03` and this
  release's commit.
- **Reading future numbers.** A move within `1.xx` needs only the steps in
  [Moving to a new release](../README.md#moving-to-a-new-release). A move to `2.0` will
  also need the changes its release notes list.

## Evidence and limits

- **A policy, not a measured result.** This is the owner's decision on numbering. No
  breaking release has happened under it yet.
- **No acting-session test ran.** The skill evidence is the same as in v0.8.

## Rollback

Pin `v1.02`. Nothing in a project changes unless its owner adopts v1.03.
